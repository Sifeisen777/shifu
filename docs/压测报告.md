# 秒杀链路压测报告

## 1. 测试目标

秒杀链路采用「Redis + Lua 预扣库存 → RocketMQ 异步落库」，请求线程只做资格判定与消息投递，不直接写订单表。本次压测验证三件事：

1. 瞬时高并发下是否超卖、是否重复下单；
2. 端到端延迟分布与吞吐能力；
3. 链路上的实际瓶颈，并为配置调整提供依据。

## 2. 测试环境

| 项 | 配置 |
| --- | --- |
| 机器 | Intel i9-14900HX（24 核 32 线程）/ 16 GB / Windows 11 |
| 运行时 | JDK 17.0.11，Spring Boot 3.5.16 |
| 存储与中间件 | MySQL 8.0.46、Redis 8.4.0、RocketMQ 5.3.4（单机 Broker，1 GB 堆，ASYNC_FLUSH） |
| 压测工具 | Apache JMeter 5.6.3 |
| 部署形态 | 压测客户端与服务端同一台机器，全部请求走 `127.0.0.1` |

单机同压的取舍：省去网络与网关损耗，但压测进程、应用、数据库、消息队列争抢同一份 CPU 与磁盘，指标比独立压测机更保守。下文所有结论都基于这一前提。

应用侧生效的关键参数：

| 参数 | 取值 |
| --- | --- |
| `server.tomcat.threads.max` | 200（默认） |
| `server.tomcat.accept-count` | 1000 |
| `spring.data.redis.lettuce.pool.max-active` | 64 |
| HikariCP `maximum-pool-size` | 10（默认） |
| 应用日志级别 | INFO |

## 3. 测试模型

- **用户**：500 个独立测试账号，每人预置独立登录态，互不干扰，因此「一人一单」限制不会掩盖库存竞争。
- **商品**：权益卡 9001，Redis 与 MySQL 两侧库存同时置为 100。
- **流量**：500 线程，1 秒内全部发起，每个线程请求一次；不使用循环，保证每个用户只产生一次下单动作。
- **校验**：以 HTTP 响应、Redis 库存与下单记号集、MySQL 订单数与库存三方交叉校验，任一不一致即判定失败。

脚本与夹具见 [`perf/`](../perf/README.md)，可重复执行。

## 4. 测试结果

### 4.1 正确性

三轮独立执行，每轮开始前重置库存与订单，结束后立即校验：

| 轮次 | HTTP 2xx | 成交订单 | MySQL 库存 | Redis 库存 | 唯一下单用户 | 超卖 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 500 | 100 | 0 | 0 | 100 | 0 |
| 2 | 500 | 100 | 0 | 0 | 100 | 0 |
| 3 | 500 | 100 | 0 | 0 | 100 | 0 |

三轮共 1500 次请求：成交 300 单，库存精确归零，订单数与唯一下单用户数一致，无超卖、无重复下单、无请求失败。

两种拒绝分支单独验证：

```
# 库存耗尽后的落选用户
{"success":false,"errorMsg":"库存不足"}

# 已持单用户再次请求（补回 1 件库存后触发）
{"success":false,"errorMsg":"不能重复下单"}
```

Lua 脚本先判库存再判一人一单，因此售罄后重复请求会统一返回「库存不足」。两种结果都是拒绝下单，不影响一致性，属于提示文案层面的取舍。

### 4.2 延迟与吞吐

| 轮次 | 500 请求耗时 | 峰值吞吐 | P50 | P90 | P95 | P99 | 最大 | 服务端 P50 | 服务端 P99 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.78 s | 639 /s | 615 ms | 726 ms | 736 ms | 762 ms | 779 ms | 194 ms | 241 ms |
| 2 | 0.64 s | 782 /s | 536 ms | 586 ms | 604 ms | 624 ms | 638 ms | 165 ms | 254 ms |
| 3 | 0.58 s | 867 /s | 488 ms | 528 ms | 544 ms | 566 ms | 571 ms | 122 ms | 221 ms |

- **峰值吞吐**为「最后一个响应结束 − 第一个请求发出」窗口内的等效处理速率（500 ÷ 窗口），平均在 640 ~ 870 次/秒。
- **端到端**口径包含 TCP 建连；500 线程瞬时建连时，建连 P50 达 353 ~ 418 ms，占端到端耗时的六成左右。剔除建连后的**服务端耗时** P50 为 122 ~ 194 ms、P99 为 221 ~ 254 ms，更能反映接口本身的开销。
- 三轮数据逐轮收敛，说明预热后指标稳定；第一轮受 JIT 与连接池冷启动影响，数值偏高。

### 4.3 异步落库时延

单独采集一轮（500 请求在 682 ms 内处理完毕），以 100 ms 粒度轮询订单表：

| 指标 | 数值 |
| --- | --- |
| 首笔订单落库 | 最后一笔响应后 ≤ 340 ms |
| 100 笔订单全部落库 | 最后一笔响应后 ≤ 1.7 s |

请求线程在消息投递成功后即返回，写库由消费者完成。100 笔订单集中在不到 2 秒内落库，未出现消息堆积或丢失，Redis 预扣与 MySQL 库存最终一致。

## 5. 瓶颈定位与调优

### 5.1 连接排队：Tomcat accept 队列

首次压测出现 393 次 `Connection refused`，且失败请求的耗时约 1 ms。定位为瞬时 500 个新连接涌入，默认 accept 队列（100）被打满，内核直接回 RST。

将 `server.tomcat.accept-count` 调整为 1000 后，1500 次请求零连接失败。该参数已写入 `application.yaml`。

> 该现象同时说明：秒杀场景的连接数远高于线程数，只调线程池无法解决建连被拒的问题，入口的排队能力同样需要放宽。

### 5.2 Redis 连接池

秒杀请求在单次调用中要访问 Redis 三次（登录态读取、订单号序列、Lua 扣减），默认 `max-active: 10` 时，200 并发下线程大量排队等连接。

| 配置 | 200 并发端到端均值 |
| --- | --- |
| `max-active: 10` | 295 ms |
| `max-active: 64` | 185 ms |

已调整为 64 / max-idle 32 / min-idle 8。

### 5.3 未采纳：数据库连接池

首页读接口在 500 并发下服务端 P99 达 1.6 s，一度怀疑是 HikariCP 默认 10 条连接导致。试调至 32 后指标无明显改善（P50 由 1447 ms 变为 1520 ms），确认瓶颈在查询本身与单机磁盘 IO，因此未合入该改动。

这条对照也说明秒杀链路的写压力确实被剥离开了数据库：同为 500 并发，读接口 P99 是秒杀接口的数倍。

## 6. 结论

- 三轮共 1500 次并发请求，成交 300 单、库存精确归零、零超卖、零重复下单。
- 单机环境下，500 请求在 0.58 ~ 0.78 s 内处理完毕，等效吞吐 640 ~ 870 次/秒；服务端 P99 稳定在 220 ~ 254 ms。
- 订单异步落库在 1.7 s 内完成，请求链路不受写库影响。
- 已根据实测调整两处配置（accept 队列、Redis 连接池），调整前后均有对比数据。

## 7. 局限与后续

- 压测客户端与服务端同机，CPU 与磁盘争用会压低绝对指标，数据适合做纵向对比，不宜直接外推为线上容量。
- 未覆盖多实例部署、网关限流、网络抖动与 Broker 独立部署后的表现。
- 未做长时间稳定性压测（当前为瞬时脉冲模型）；若用于容量评估，需补充 10 分钟以上的阶梯加压与 24 小时稳定性观察。
- 消费者当前单机单组，消息堆积能力未经压测验证。

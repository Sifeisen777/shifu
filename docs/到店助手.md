# 到店助手

面向到店场景的问答能力：用户可以用自然语言询问商户、优惠券与已购权益，回答基于平台真实数据，可跳转到对应记录。

## 一、能力范围

| 用户问题 | 数据来源 | 工具 |
| --- | --- | --- |
| 附近有什么好吃的 / 某类店有哪些 | `biz_merchant` | `search_merchants` |
| 这家店在哪、几点营业 | `biz_merchant` | `get_merchant_detail` |
| 这家店有什么券、多少钱 | `biz_benefit` + Redis 秒杀库存 | `list_merchant_benefits` |
| 我买的券还能用吗 | `biz_benefit_order` | `list_my_benefits` |

超出上述范围的问题（闲聊、编程、时事）由系统提示词约束为一次范围说明，并给出可咨询的方向。

## 二、请求链路

```
前端抽屉面板
  └─ POST /assistant/chat（SSE）
       ├─ 登录态解析：游客与登录用户都可提问
       ├─ 限流：assistant:rate:{userId | ip}
       ├─ 装配只读工具（注入当前用户身份）
       ├─ ChatClient + 会话记忆 Advisor
       │    ├─ 模型决定是否调用工具
       │    ├─ 工具查询 MySQL / Redis 返回结构化结果
       │    └─ 模型组织语言后逐段返回
       └─ 降级：模型不可用时返回规则应答
```

## 三、工具设计约束

**只读。** 工具集中不包含下单、秒杀、退款等写操作。交易类动作仍由页面按钮走原有接口，库存原子扣减与订单幂等由 Lua 脚本和消费端保证，不因模型介入被绕过。

**身份不可由模型指定。** `list_my_benefits` 不接受用户 id 参数。登录用户由服务端在请求线程解析，随后注入工具实例；模型即使被要求「查询其他用户的订单」，也没有可传参的入口。

**登录上下文需在构造时固化。** 工具在模型回调线程执行，`UserHolder` 的 ThreadLocal 在该线程为空，因此不能像普通 Service 那样在方法内部取当前用户。工具实例按请求创建并携带 userId，规避了跨线程取值的问题。

**泛词处理。** 「附近」「好吃」这类口语词按名称检索必然为空，工具会识别修饰词并去掉后重试；仍无命中时退回按评分推荐，并在结果中说明，避免给用户一个空答案。

## 四、模型与会话

- 接入方式：Spring AI `ChatClient` + OpenAI 兼容协议，默认指向 DeepSeek，切换模型只需改 `base-url` 与 `model`
- 系统提示词：`src/main/resources/prompts/assistant-system.md`，约束回答边界、事实来源与不承诺事项
- 会话记忆：`RedisChatMemoryRepository` 以 `assistant:memory:{sessionId}` 保存最近 20 条消息，两小时过期；工具调用的中间过程不入记忆，避免上下文膨胀
- 流式下发：模型按 token 返回，中文常单字成段，服务端按 8 段或 120ms 合并后推送，降低 SSE 帧数

## 五、成本与稳定性

| 机制 | 说明 |
| --- | --- |
| 限流 | 单用户 / 单 IP 十分钟内 20 次，Redis 计数，异常时放行 |
| 输出上限 | `spring.ai.openai.chat.options.max-tokens`，默认 800 |
| 用量记录 | 每轮对话记录 prompt / completion token 数与耗时 |
| 降级 | 模型超时、额度耗尽、密钥缺失时返回关键字规则应答，入口不中断 |
| 缓冲控制 | 响应头 `X-Accel-Buffering: no`，避免 nginx 缓冲导致整段返回 |

## 六、配置

```yaml
spring:
  ai:
    openai:
      api-key: ${DEEPSEEK_API_KEY:disabled}     # 未配置时进入规则应答模式
      base-url: ${DEEPSEEK_BASE_URL:https://api.deepseek.com}
      chat:
        options:
          model: ${DEEPSEEK_MODEL:deepseek-chat}
          max-tokens: ${ASSISTANT_MAX_TOKENS:800}
shifu:
  assistant:
    enabled: true
    rate-limit: { max-requests: 20, window: 10m }
    memory:     { max-messages: 20, ttl: 2h }
```

密钥放在 `config/application-secret.yaml`（已忽略提交），或使用环境变量 `DEEPSEEK_API_KEY`。仓库内只保留 `config/application-secret.yaml.example`。

## 七、验证方式

```bash
# 助手状态
curl http://127.0.0.1:8080/api/assistant/config

# 流式问答
curl -N -X POST http://127.0.0.1:8080/api/assistant/chat \
  -H "Content-Type: application/json" \
  -d '{"sessionId":"smoke-test-0001","message":"拱宸桥附近有什么烤肉"}'
```

观察应用日志中 `客服回答完成` 一行，可看到会话 id、登录用户、字数、耗时与 token 用量。将 `api-key` 置为非有效值时，同一请求应返回规则应答而不是错误。

## 八、边界

- 不代用户执行交易，不承诺退款时效与赔付
- 不接入实时库存之外的数据源，秒杀库存直接读 Redis，避免与数据库出现偏差
- 未接入向量检索：当前知识以结构化数据为主，规则类问题由系统提示词覆盖；如需接入政策类长文档，可在此基础上增加检索环节

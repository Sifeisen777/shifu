# 账号认证与关注关系

## 1. 登录方式

`POST /user/login` 同时支持两种凭据，按请求体携带的字段分流：

| 方式 | 请求体 | 行为 |
| --- | --- | --- |
| 验证码 | `{ "phone", "code" }` | 校验 Redis 中的验证码；手机号未注册时自动创建账号 |
| 密码 | `{ "phone", "password" }` | 校验密码哈希；账号不存在或密码未设置均返回同一错误 |

两种方式共用同一套令牌发放逻辑，返回登录令牌并写入 `login:token:{token}`（Hash，有效期由 `LOGIN_USER_TTL` 控制），后续请求通过 `authorization` 请求头携带。验证码登录时若同时携带 `password`，新账号会一并设置初始密码。

「账号不存在」与「密码错误」返回相同提示，避免通过响应差异枚举已注册手机号。

## 2. 密码存储

密码使用 PBKDF2-HMAC-SHA256：每次生成 16 字节随机盐，迭代 120000 次，摘要 256 位，比对采用常数时间比较。密文格式为 `pbkdf2$迭代次数$盐$摘要`，算法参数随密文保存，后续调整计算强度时旧密码仍可校验，无需全量重置。

`sys_user.password` 为空表示尚未设置密码，该账号只能使用验证码登录。

`PUT /user/password`（需登录）用于设置或修改密码：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `password` | 是 | 长度 6~32 位 |
| `oldPassword` | 已设置密码时必填 | 首次设置留空 |

修改已有密码必须校验原密码，防止会话被冒用后直接改密。

## 3. 关注关系与计数

`biz_follow` 记录关注关系，`(user_id, follow_user_id)` 上有唯一索引，并发重复关注由数据库兜底拒绝；应用侧在写入前先判存在性，重复点击直接返回成功。

`sys_user_profile.fans` 与 `followee` 是关系表的派生字段，写入约定如下：

- 关注 / 取关在同一事务内写入关系表，随后按关系表重新统计双方的计数；
- 采用重算而非自增自减，规避并发下的丢失更新；
- 计数写入使用 upsert，用户尚无资料行时也能落库；
- `FollowCountInitializer` 在每次应用启动时按关系表校准一次，用于修正历史数据与计数漂移，重复执行结果一致。

`GET /user/info/{id}` 直接返回资料行中的计数；用户从未填写资料时返回零值对象，前端无需区分「无资料」与「计数为 0」。

已在运行的数据库可执行 `src/main/resources/db/migration-follow-count.sql` 补齐唯一索引并校准历史计数；新部署直接导入 `shifu.sql` 即可。

## 4. 相关接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/user/code` | 发送验证码 |
| `POST` | `/user/login` | 验证码 / 密码登录 |
| `PUT` | `/user/password` | 设置或修改密码 |
| `PUT` | `/follow/{id}/{isFollow}` | 关注 / 取关 |
| `GET` | `/follow/or/not/{id}` | 查询关注状态 |
| `GET` | `/follow/common/{id}` | 共同关注 |
| `GET` | `/user/info/{id}` | 资料与粉丝 / 关注数 |
